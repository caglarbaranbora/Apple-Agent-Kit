# Level 4 Review #0003 — Tier 2, L4.5 (citation content verification)

Date: 2026-08-23
Corpus: 13 of 17 Tier 2 domains attempted; coverage varies by domain (see Coverage below).

## Why

Reviews #0001 and #0002 explicitly left L4.5 open: does the Apple page a rule cites
actually say what the rule quotes it as saying? Both prior reviews read the repository;
neither fetched a single external page. `check_links.py` proves a URL resolves and
isn't a stale redirect — it does not read the page. This review closes that gap for as
much of Tier 2 as time allowed, and is explicit about the part it didn't reach.

## Method

Modern `developer.apple.com/documentation/*` pages are a client-rendered SPA — a direct
fetch returns only the `<title>` tag, no body. Workaround found and used throughout:
`developer.apple.com/tutorials/data/documentation/<same-path>.json` returns the same
page's Abstract/Discussion/Example Usage as real text. WWDC video-session pages and
`library/archive/...` legacy pages fetch directly with no workaround needed.

For every Rule's Apple quotation in scope, the cited URL was fetched and the quoted
sentence checked against the live page: present and accurate, present but reworded
(substance intact, not a defect), or absent/contradicted (a defect).

## Confirmed defects (10), all fixed

**`usernotifications/notification-delegate-handling.md` Rule 1** — quoted "Always
assign an object to the delegate property before performing any tasks that might
interact with that delegate," attributed to `UNUserNotificationCenterDelegate`'s own
page. That sentence appears on neither that page nor the `.delegate` property page.
The `.delegate` property's real text: "To guarantee that your app responds to all
actionable notifications, you must set the value of this property before your app
finishes launching. For an iOS app, this means updating this property in the
`application(_:willFinishLaunchingWithOptions:)` or
`application(_:didFinishLaunchingWithOptions:)` method of the app delegate." The rule's
substance (assign early) was right; the quote was fabricated. Replaced with the real
text; added the `.delegate` property URL to `references:`/`## References`.

**`usernotifications/notification-delegate-handling.md` Rule 4** — quoted "Match the
value in the [actionIdentifier] property of the response object to one of your app's
actions or a system-defined action," attributed to `didReceive`. Not on that page or
`actionIdentifier`'s own page. Real `actionIdentifier` text: "This parameter may
contain the identifier of one of your `UNNotificationAction` objects or it may contain
a system-defined identifier. The system defined identifiers are
`UNNotificationDefaultActionIdentifier` and `UNNotificationDismissActionIdentifier`."
Same shape as Rule 1: correct rule, fabricated quote. Fixed the same way.

**`core-data/managed-object-context-crud.md` Rule 4** — quoted a comparison of
`perform(_:)`/`performAndWait(_:)` ("ensure the block operations execute on the correct
queue... returns immediately... doesn't return until the block completes") that does
not appear on either method's page. `perform(_:)`'s entire current Discussion is one
sentence about `processPendingChanges()`; the async/sync contrast is real but must be
sourced from each method's own Abstract, not a single combined quote. Rewrote using
both pages' actual Abstract text; added the `performAndWait(_:)` URL (disambiguation
suffix `-ypye`) to `references:`/`## References`.

**`core-data/managed-object-context-crud.md` Rule 5** — quoted "fetch and save
operations are mediated by the parent context instead of a coordinator... a parent does
not pull changes from children before it saves," attributed to `parent`. Not on that
page (which only says `nil` means no parent, see Parent store) or on `save()`'s page in
that form. `save()`'s actual text: "If a context's parent store is another managed
object context, then `save()` only updates managed objects in that parent store. To
commit changes to the external store, you must save changes in the chain of contexts up
to and including the context whose parent is the persistent store coordinator." Fixed
by re-sourcing from `save()`'s real text (already in `references:`).

**`storekit/transaction-updates-and-restoring-purchases.md` Rule 3** — completed a real,
truncated Apple quote with the opposite of what Apple actually says. Apple: "after a
successful in-app purchase on the same device, StoreKit returns the transaction through
`Product.PurchaseResult.success(_:)`" — i.e. same-device purchases are *not* re-emitted
through `Transaction.updates`. The Contract's version finished the sentence with "...
through the updates sequence too," asserting the reverse. This is the highest-severity
defect this pass found: the rule's conclusion (don't rely on `Transaction.updates` as
the restore mechanism) still holds, but for a different and stronger reason than
stated — the listener doesn't just lack an on-demand trigger, it never sees same-device
purchases at all. Fixed with the real quote.

**`authenticationservices/session-persistence-and-sign-out.md` Rule 2** — cited
`sign-in-with-apple-request-and-credential` Rule 5 for "`email` is `nil` after the
first authorization." That Contract's Rule 5 is about `ASAuthorizationError.Code`
handling; the email/fullName-nil claim is its Rule 4. Fixed the citation number.

**`authenticationservices/session-persistence-and-sign-out.md` Rule 4** — cited
`nonce-and-identity-token-verification` Rule 6 for `authorizationCode` handling; that
Contract has 5 Rules total, no Rule 6. The `authorizationCode`-is-short-lived claim is
its Rule 5. Fixed the citation number.

Neither wrong rule-number was caught by review #0001/#0002's Bound A ("do citations
resolve"), because Bound A checked citation *ids*, not citation *numbers* against the
target's actual rule count — a narrower gap than L4.4 as scoped previously covered.

**`passkit/adding-passes-ui.md` Rule 4** — quoted `PKAddPassButton`'s Abstract as "you
choose the type and style of button, and the system provides a control with the correct
content and appearance." That exact sentence is `PKPaymentButton`'s Abstract (a
different symbol, in `apple-pay-payment-request.md`) — `PKAddPassButton`'s real text is
"you choose the button's style, and the system provides a control with the correct
appearance." Fixed with the real quote.

**`passkit/adding-passes-ui.md` Rule 5 — the largest finding of this review, a false
scope claim rather than a citation slip.** The rule read: "MUST NOT expect a SwiftUI-
native equivalent... `PKAddPassesViewController` and `PKAddPassButton` are documented
only for iOS, iPadOS, Mac Catalyst, and visionOS with no SwiftUI counterpart in
PassKit's topic index." This is false and has been false since iOS 16: `PassKit` ships
`AddPassToWalletButton`, documented as "the SwiftUI equivalent to `PKAddPassButton`,"
whose initializer takes the passes and a completion closure directly — replacing not
just the button's appearance but the whole present/delegate/dismiss flow Rules 1-3
govern. Confirmed independently via WWDC22's "What's new in Wallet and Apple Pay" and
Apple's own `AddPassToWalletButton` reference page, not just the citing Contract.

This is the same *class* of defect the Tier 3 pilot found in `photos` (slice #0007,
`picker-and-selection-results` vs. wrapping) and that review #0001's T2-01 fixed for
this exact Contract in the opposite direction — T2-01 recorded the coupling as "wrap
`PKAddPassesViewController` in a `UIViewControllerRepresentable`," which was correct
*given* the premise that no SwiftUI-native control existed. That premise was wrong.
Rewrote Rule 5 to require `AddPassToWalletButton` in SwiftUI and restrict the
wrap-in-representable guidance to UIKit-hosted screens; updated `## Intent`, `## Scope`,
the `## Compliant Example`, frontmatter `summary`/`tags`/`references`, and
`## References`. Also corrected the same false claim in `docs/architecture/domain-map.md`'s
PassKit scope entry, and updated `skills/passkit/SKILL.md`'s description, triggers, and
routing bullet to name `AddPassToWalletButton`.

**`tipkit/tip-options-and-app-configuration.md` Rule 2`** — quoted "By default
`.applicationDefault` is used on macOS, iOS, watchOS, and visionOS. On tvOS,
`.applicationDefault` is used by default in conjunction with `NSUbiquitousKeyValueStore`
to manage tip statuses." Apple's actual text: "by default `URL.applicationSupportDirectory`
is used on macOS, iOS, watchOS, and visionOS. On tvOS, `URL.cachesDirectory` is used by
default in conjunction with `UserDefaults` to manage tip statuses." The Contract
substituted `NSUbiquitousKeyValueStore` (iCloud-synced) for `UserDefaults` (local) — a
materially different persistence and privacy mechanism, not a wording nit. Fixed.

**`passkit/apple-pay-authorization-and-result-handling.md` Rule 4`** — minor. The
bracketed cross-reference read `[didAuthorizePayment(_:handler:)]`, silently
"modernizing" Apple's own citation. Apple's `paymentAuthorizationControllerDidFinish(_:)`
page still names the older `paymentAuthorizationController(_:didAuthorizePayment:completion:)`
overload in that sentence, not the `:handler:` variant this Contract's other rules use.
The sequencing described applies identically to both overloads, so this doesn't change
the rule's correctness — fixed by quoting Apple's actual (still-`:completion:`) text and
noting the overload difference explicitly rather than silently substituting.

## A link-freshness defect found as a side effect, not L4.5 itself

**`privacy/tracking-domains-and-third-party-sdk-signatures.md`** cited
`https://developer.apple.com/support/third-party-sdk-requirements/` (lowercase `sdk`,
trailing slash). That URL serves a soft 404 — Apple's real "page can't be found"
template, at HTTP 200 — so `check_links.py`'s status-code check passed it and this
review's first pass mistook the soft-404 body for a hard failure before finding the
real cause. The correct, live URL is `https://developer.apple.com/support/third-party-SDK-requirements`
(capital `SDK`, no trailing slash), confirmed via direct fetch and independently via
search. This is a class `check_links.py` cannot catch by design (a 200 status with dead
content, not a redirect) and worth naming for future link-freshness passes rather than
assuming a 200 means the content is real.

## Ruled out — fork-reported, contradicted on independent re-check

Two items the delegated audit reported as defects did not hold up under a direct
re-fetch from this session:

- `passkit/apple-pay-payment-request.md` Rule 1 was reported as citing
  `present(completion:)` instead of `canMakePayments()`. A direct fetch of the cited
  `canMakePayments()` page's Discussion shows the exact comparison the Rule quotes,
  naming `canMakePayments()`/`canMakePayments(usingNetworks:)` as the Rule states. No
  defect; not changed.
- `app-intents/app-intent-declaration-and-parameters.md` Rule 3's `CaseDisplayRepresentable`
  citation was flagged as needing verification. A direct fetch of `AppEnum`'s page
  confirms `CaseDisplayRepresentable.caseDisplayRepresentations` is a real, required
  conformance path. No defect; not changed.

Both are recorded to make clear that a delegated audit's report was itself re-verified
before any fix was applied, per this repository's evidence-over-assertion standard —
and as a caution that L4.5 findings from any single fetch, delegated or direct, warrant
a second look before they're trusted enough to edit a Contract.

## Second pass — the remaining four domains, done directly rather than delegated

The first pass left `eventkit`'s last quote, `testing`, `security`, `backgroundtasks`,
and three of `app-intents`'s four Contracts unchecked. This pass closes all of them,
fetched directly in this session rather than through a sub-agent.

**`eventkit`'s open item — resolved, not a defect.** The `recurrence-rules-and-eventkitui-handoff.md`
Rule 4 claim about EventKitUI running "outside your app's process" on iOS 17 is confirmed
by WWDC23 session 10052 ("Discover Calendar and EventKit"): "In iOS 17, this UI runs in
a separate process, which means you don't need to request Calendar access." Same
substance, paraphrased rather than verbatim in the Contract — not a fabrication, no fix.

**`security` — 4/4 Contracts, ~20 citations checked, 0 defects.** Every quote in
`keychain-item-crud`, `keychain-accessibility-levels`, `keychain-access-groups-and-sharing`,
and `storing-structured-data-in-keychain` verified exact against its cited page,
including the multi-page cross-check needed for `keychain-access-groups-and-sharing`
Rule 4's "always an invalid group" phrase, which only appears on `kSecAttrAccessGroup`'s
own page, not the guide article also cited for related claims. The one domain of the
four checked this session with zero findings of any kind.

**`testing` — 5/5 Contracts, ~30 citations checked, 4 fabricated-or-imprecise quotes
fixed, all minor (correct rule, wrong exact wording):**
- `xctest-case-structure-and-assertions.md` Rule 4 attributed "to compare two
  non-optional values of the same type" to `XCTAssertEqual` in quotes; the real
  Abstract is "Asserts that two values are equal." Reworded to quote the real text and
  state the non-optional/`Equatable` constraint as the type-system fact it is, not a
  quotation; added the missing `XCTAssertEqual` citation.
- `swift-testing-fundamentals.md` Rules 2 and 3 each tightened a paraphrase-presented-as-quote
  to Apple's actual sentence (`#expect` "allows your test to continue running even when
  the condition fails"; `#require` "throws an instance of `ExpectationFailedError`").
- `expectations-for-asynchronous-code.md` Rule 1 quoted XCTest offering expectations for
  "asynchronous blocks in dispatch queues, delegate methods, asynchronous callbacks,
  closures, or completion blocks" -- a composite that doesn't exist verbatim anywhere.
  Apple's real opening sentence: "asynchronous code doesn't execute directly within the
  current flow of code. This might be because the code runs on a different thread or
  dispatch queue, in a delegate method, or in a callback, or because it's a Swift
  function marked with `async`." Fixed.

**`backgroundtasks` — 4/4 Contracts, ~20 citations checked, 0 fabricated quotes but 1
currency finding: `submit(_:)` is now deprecated.** Apple's live `BGTaskScheduler`
reference marks `submit(_:)` deprecated as of iOS/iPadOS/tvOS 27.0 and visionOS 1.0, in
favor of `submitTaskRequest(_:completionHandler:)` -- itself still Beta at the time of
this review. Rather than rewrite the whole Contract around an unstable replacement API
(the deployment-target math means most callers are still on `submit(_:)` for now), added
a note to `background-task-registration-and-scheduling.md` Rule 4 naming the deprecation
and directing agents to verify the replacement's current signature once it stabilizes.
This is the same *shape* of finding as `passkit/adding-passes-ui` Rule 5 -- an API
surface moved out from under a Contract -- caught only because this pass fetched the
live page rather than trusting the citation resolved.

**`app-intents`'s remaining three Contracts — 3/3, ~20 citations checked, 3 fixes:**
- `app-entities-and-queries.md` Rule 1's quoted ID-type list read "`String`, `Int`, or
  `UUID`"; Apple's real order is "`UUID`, `String`, or `Int`." Corrected the order inside
  the quotation.
- `app-entities-and-queries.md` Rule 4 quoted Siri using queries to "resolve
  conversational requests automatically" -- not a real phrase. The App Intents docs have
  been reorganized since this Contract was written (a new `entity-queries` guide page now
  exists, not yet in this Contract's `references:`); its actual text is "resolve natural
  spoken language into one of your app's entities." Fixed and added the new page to
  `references:`/`## References` and to `references/apple/app-intents.md`'s `## Source`.
- `intent-results-and-widget-hookup.md` Rule 4 quoted `OpensIntent` as "The result of
  performing an action that delivers an app intent back to the initiator of the action"
  -- a plausible-sounding composite matching the *pattern* of `ReturnsValue`'s and
  `ProvidesDialog`'s real abstracts, but not `OpensIntent`'s own. `OpensIntent`'s actual
  abstract reads differently: "A result type that indicates your app intent returns
  another app intent." Fixed.
- `app-shortcuts-and-siri-phrases.md` Rule 1's quote was independently confirmed exact,
  but sourced from `getting-started-with-the-app-intents-framework`, a page this Contract
  hadn't cited -- added to `references:`/`## References`.

**A genuine tooling limit, not a defect, hit and confirmed rather than guessed
around.** Two quotes in `app-shortcuts-and-siri-phrases.md` Rule 2/3 cite Apple's Human
Interface Guidelines (`developer.apple.com/design/human-interface-guidelines/app-shortcuts`).
Unlike `documentation/*` pages, HIG pages have no working `/tutorials/data/...json`
equivalent -- confirmed by testing the pattern directly and getting a 404, then
confirming the plain HIG URL still returns title-only like the original SPA-blocking
problem. WebSearch surfaces adjacent WWDC-session paraphrases of the same guidance but
never the literal HIG page text. These two quotes are left as **unverified by
available tooling**, not confirmed correct or confirmed wrong -- a distinct status from
every other citation in this review, and named rather than silently passed.

  tried (direct fetch, the `/tutorials/data/...json` workaround, or web search for the
  literal text). A future pass with different tooling (or a human check in-browser)
  should close these two specifically.

## Conclusion

Fourteen real defects fixed, plus one currency note (`backgroundtasks`' `submit(_:)`
deprecation) that isn't a citation error but the same underlying risk. One fix
(`passkit/adding-passes-ui` Rule 5) is a scope-level error on the same order as the
Tier 3 pilot's `PHAsset.location` finding — a Contract asserting a negative ("no
SwiftUI equivalent exists") that had gone stale as Apple shipped one, silently
invalidating a coupling review #0001 had explicitly verified under the premise that
held at the time. L4.5 findings cluster in exactly the way the
checklist predicts: fabricated-but-plausible quotes attached to correct rules, which no
amount of repository-only reading (L4.1-L4.4) could ever have caught, since the defect
is invisible until the cited page is actually read. Every Tier 2 domain has now had
every citable rule's Apple quotation checked against live content at least once, with
two exceptions named rather than silently passed: the HIG quotes tooling cannot fetch,
and the handful of reference-only citations with no attached quotation to check in the
first place. Combined with reviews #0001 and #0002, Tier 2's 78 Contracts and 17 Skills
have now had all five Level 4 checks (L4.1-L4.5) run against the full corpus.
