# Level 4 Review #0001 — Tier 2

Date: 2026-08-08
Corpus: 78 Knowledge Contracts across the 17 Tier 2 domains, plus their Skills.

## Why

Tier 2 was built before `docs/contributing/review-checklist.md` existed. Phase 5b's
read-through covered `human-interface-guidelines` and `style-guide` — both Tier 1 — so
**no Tier 2 domain had ever been read against Level 4.**

The prior assessment that "Tier 2 conforms" rested on Levels 1-3 passing, on the nine
stale scope claims splitting proportionally between tiers, and on 27 of 31 declared
boundaries being classified. Every one of those is mechanical, and Phase 7's whole
finding was that the mechanical checks are not the ones that catch semantic defects.
The assessment was over-claimed and this review is what it should have rested on.

This is the first Level 4 review recorded under `validation/reviews/`, which exists so
that a level marked blocking leaves the same evidentiary trail Level 5 does.

## Method

Two mechanical bounds first, so reading was aimed rather than exhaustive — the approach
Phase 5b's 196-term check established.

**Bound A — dangling rule citations (L4.4, mechanical half).** Every prose reference of
the form `` `knowledge.x.y` Rule N `` checked against the target's actual rule count.

    0 findings, repository-wide.

**Bound B — API symbols claimed by rules in more than one domain (L4.2, L4.3).** Every
backtick-quoted identifier inside a `## Rules` section, mapped to the domains claiming
it. Duplication and coupling both live where two domains state rules about the same
symbol; this bounds where to read.

    1,604 distinct symbols in Rules
       97 claimed by more than one domain
       88 of those touch Tier 2

Most are Swift vocabulary (`Codable`, `Data`, `async`, `struct`) and were discarded. The
rest were read.

## Findings

### T2-01 — Two Contracts state a mechanic without naming its owner

Status: **Blocking** — fixed

`UIViewControllerRepresentable` carries rules in three domains:

| Contract | States |
|---|---|
| `uikit/swiftui-view-representable` Rule 5 | use it for a `UIViewController`, and **do not** wrap the controller's `view` in a `UIViewRepresentable` — that leaves the controller outside the containment hierarchy |
| `eventkit/recurrence-rules-and-eventkitui-handoff` Rule 6 | EventKitUI is UIKit-only; bridge it with `UIViewControllerRepresentable` |
| `passkit/adding-passes-ui` Rule 5 | wrap `PKAddPassesViewController` in a `UIViewControllerRepresentable` |

The domain facts are correctly owned — each framework owns "I have no SwiftUI-native
equivalent." What was missing is the delegation sentence. `eventkit`'s `related` named
only its own domain; `passkit`'s was `related: []`. Neither Excluded list mentioned the
wrapping mechanic.

So an agent told to wrap `PKAddPassesViewController` never reaches the constraint that
makes the wrap correct. This is the Phase 5b pattern exactly — one owner states the
rule, the neighbour must point and say it defines none — recurring in a tier that
read-through never covered.

**`photos` would have been the third instance.** Its pre-classification in
`domain-map.md` said the mechanic "is not duplicated here", which was right about
duplication and silent about the pointer. It is now classified **coupled**, with the
requirement to name `knowledge.uikit.swiftui-view-representable` Rule 5.

Fixed: both Contracts now name the owner and carry the `related` edge.

### T2-02 — A one-way cross-reference

Status: Minor — fixed

`foundation/codable-encoding-and-custom-conformance` cross-references
`networking/codable-decoding` in both prose and `related`. The reverse edge was absent.
Both state the same anti-default rationale about `.deferredToDate` on opposite sides of
one API pair, and the boundary is correctly classified in `domain-map.md`. Same shape as
Phase 5b's `dark-mode` → `accessibility` finding: not duplication, an edge that ran one
way.

### T2-03 — The classification vocabulary had no value for coupling

Status: **Structural** — fixed

`Cross-Domain Notes` used two values, angle-split and clean handoff. Both answer *do
these overlap?* Neither records *does a choice on one side fix a choice on the other?*

Two boundaries classified as clean handoffs produced defects anyway —
`widgetkit` ↔ `app-intents` (slice #0002) and `local-authentication` ↔ `security`
(slice #0005). Both classifications were **correct about overlap**. The vocabulary had
no way to be wrong, and no way to be complete.

A third value, **coupled**, is now defined and requires naming which side owns the
coupling rule.

### T2-04 — A boundary classified against an unbuilt domain, never revisited

Status: **Structural** — fixed

`widgetkit`'s entry read that it "proactively deferred two seams to domains not yet
built." Both shipped. Nobody returned. Slice #0002's defect is downstream of that.

This is the `check_scope_vocabulary` defect one layer up — a scope claim that was true
when written and rotted when a neighbour shipped — except it lives in `domain-map.md`,
which no check reads. The rule is now written down: a boundary classified against an
unbuilt domain MUST be revisited when that domain ships.

### T2-05 — Four boundaries never classified at all

Status: Fixed

`localization` ↔ `sf-symbols`, `app-store-review-guidelines` ↔ `localization`,
`app-tracking-transparency` ↔ `privacy`, `app-store-review-guidelines` ↔
`authenticationservices`. All four are clean handoffs; all four now say so. Notably ATT
had three boundaries, two written down and one not.

## Passes

Recorded because a review that only reports defects cannot be distinguished from one
that stopped early.

- **L4.4, mechanical half** — 0 dangling rule-number citations, repository-wide.
- **L4.6** — 0 Skills state a rule. No `MUST`/`SHOULD` appears in any Skill's Purpose or
  Routing section, in either tier.
- **Authorization is not duplicated across five permission-gated domains.** `ATT`,
  `eventkit`, `usernotifications`, `passkit`, and `authenticationservices` each state a
  genuinely different shape: one-time-per-decision, `.fullAccess` vs `.writeOnly` as
  non-interchangeable grants, `.provisional` as its own status. `passkit`'s Rule 5 goes
  further and forbids the false generalization by name — "MUST NOT model PassKit's
  pass-library access as an EventKit-style permission state machine." That rule is the
  best evidence in the corpus that the partition was authored deliberately, and it
  matters for the pilot: `core-location` and `photos` add a sixth and seventh shape.
- **`UserDefaults` across five domains** — four distinct rules, and the fifth
  (`authenticationservices` Rule 3) already delegates explicitly to `security`. The
  pattern working, unprompted.
- **L4.1** — the atomicity heuristic (a summary enumerating three or more clauses) flags
  131 of 258 Contracts, half the corpus. Sampled Contracts are atomic: the enumerations
  describe one concept's API surface, not two responsibilities. Recorded as a
  **rejected check**, for the reason `validation-model.md` already gives — a heuristic
  this noisy gets silenced, so L4.1 stays a reading check.

## Conclusion

Tier 2 largely conforms, and the qualifier is load-bearing: the review found one real
duplication-class defect with two instances, and three structural gaps in how boundaries
are recorded. **T2-01 would have propagated into the pilot**, because the pilot's own
pre-classification had already been written on the assumption that "not duplicated" was
the whole question.

The instinct to review before extending was right, and the mechanical evidence that
argued against it was measuring the wrong things.
